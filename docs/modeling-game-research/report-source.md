# 醒来之前：从舞台演示到可玩的梦

## 建模质量、GitHub 工具与游戏设计的深度研究

**日期：2026-09-07 · 对象：作品创作者与下一版制作团队**

**范围：真人姥爷的正式舞台设想，以及用户已选择的独立电脑游戏原型。**

## 一、直接结论：需要游戏的行动逻辑，也需要美术的制作闭环

**值得采用游戏设计视角。** 最重要的改变，是从“按剧本播放六个画面”，变成“我试探这个世界，它回应我，我改变自己的行动，而刚才的细节在后来被认出”。游戏设计负责行动、后果、探索与试玩；戏剧仍决定这些行动为什么重要，什么时候留白，什么时候让照顾发生。

**建模质量不能靠换软件或下载一批skills直接解决。** 当前原型已经证明事件流和实时舞台能运行，但还没有证明美术达到作品需要的辨识度，更没有证明观众在没有标签提示时能认出自己的回声。下一版应把参考、造型、材质、光影、动作、真实游戏视点和导出检查连成一个可反复比较的流程。

用户随后明确选择了独立电脑游戏。当前推荐路线因此调整为 **Blender母版 + Godot实时游戏 + 原始动作记录与可选AI建议**。这不是在断言Godot画质高于Unreal；它是针对这台集显电脑、单场景叙事和可下载运行需求的制作选择。Godot官方兼容渲染最低条件包括支持OpenGL 3.3或Windows Direct3D 11的集显，实际表现仍须测本项目。[Godot系统要求](https://docs.godotengine.org/en/stable/about/system_requirements.html)

## 二、当前画面为什么仍像预演：瓶颈不只是面数

以下判断来自本项目的资产生成脚本、实时渲染代码和实际截图，是本地审查结果，不是某篇论文对本项目的评价。

| 层面 | 当前问题 | 下一版的具体改法 |
|---|---|---|
| 小熊轮廓 | 身体、头、耳为清楚的椭球拼接，能识别为熊，但缺少这只熊的身份 | 统一大小熊母版；略歪的耳朵、左袖补线、布料边与同样的口鼻比例 |
| 石板材质 | 旧版本用视空间坐标计算条纹；转视角会改变表面纹理关系 | 使用固定在物体上的UV/PBR贴图，控制真实尺度与方向；强调厚度、层理、磨圆边 |
| 服装与照顾 | 衣服显露与手臂旋转主要是状态占位，手指没有真正接住衣物 | 先让手、熊和袖口的轮廓从玩家距离可读，再处理接触与停顿；真人舞台用实际表演验证 |
| 光与构图 | 大面积亮窗、光束和大熊可能抢走姥爷怀里的小熊 | 以手部和熊为焦点做曝光与遮挡检查；有意识降低窗景对比 |
| 玩法 | 任意累计6次非呼喊动作触发太阳雨；两个90秒演示按预定时间推进 | 用首次局部回应教会世界规则，随后连续变化；让走近、停留、抱熊与交换构成可玩的路径 |

这里最应避免的误判是“网格更密，所以作品更成熟”。如果观众仍看不到姥爷在理袖，增加毛发与高模并没有改善核心体验。一个清楚的侧身、暖光中的手、可辨的停顿，可能比整间房多几百万个面更重要。

## 三、建模怎么做得更好：围绕三个重点资产组织制作

### 1. 小熊必须先成为同一只熊，再成为高质量模型

建立一份共享母版，大小熊通过缩放与表演用途区分；不要各生成一只“差不多”的熊。耳朵倾斜、口鼻颜色、左袖补线和衣服开口是两个世界之间的视觉证据。至少让一个识别特征在近距离与全景中都成立。

将头、左右耳、左右臂、袖口、衣物和接触点分开命名，保持可编辑层级。表面细节服务于柔软、被抱过、被修补的感觉；游戏端先采用细纹理与少量轮廓变化，不把昂贵的实时毛发作为“毛绒”的唯一实现。

### 2. 红窗与青绿石板应像有结构的物，而不是色块

红窗需要外框、内框、压条、窗台厚度、边缘的旧漆和内外明暗。青绿石板需要厚度、边缘尺度、细层理和低调的粗糙度变化。风化不能随机铺满：手常摸的位置、桌面边缘和窗台积尘应有不同逻辑。

可先获取少量1K或2K的真实PBR资产作参照或素材，不必下载整库。Poly Haven官方说明HDRI、纹理和模型资产采用CC0；插件代码和安装包的许可、获取方式是另外的问题。[Poly Haven资产许可](https://polyhaven.com/license)

### 3. 姥爷的模型投入应与最终用途相称

正式舞台是活人，电脑游戏才需要数字角色。因此优先做可读的肩背、侧脸、衣服垂坠、手部姿态和抱熊空间关系；不能因为游戏需要一个角色，就误把制作重点变为亲人肖像复刻。

电脑版的照顾动作需要有准备、接触、持续和松开的阶段。先做一段完整的理袖或抱熊，而非给四种动作都配一个粗略摆动。目标是无需文字说明也能认出动作；如果必须显示“A的动作回来了”才被理解，个性化仍停留在标签层。

### 4. 分步检查，比一次性生成整间房更可靠

BlenderAlchemy证明了“生成编辑方案、渲染、视觉比较、保留较好结果”的可行性；但论文实验主要针对材质与灯光，不是成熟的毛绒角色、穿衣动画或完整游戏生产系统。[Huang等，BlenderAlchemy，2024](https://arxiv.org/html/2404.17672v1)

2026年的Thinking in Blender进一步将几何、材质、构图、灯光分阶段处理，并允许换视点检查和回退；作者同时指出早期错误会传递，反复验证增加运行时间与API成本。这支持分步制作的方向，不能保证任何自动流程必然优于艺术家。[Thinking in Blender，2026预印本](https://arxiv.org/html/2606.02580v1)

据此，本项目采用：定参考与尺度 → 定轮廓 → 做材质 → 做一次关键动作 → 从玩家和侧面视点检查 → 导出 → 在游戏引擎重看。每轮只明确解决一类问题，并保留上一版作对照。

## 四、GitHub核查：哪些值得用，哪些需要改造或排除

本轮深入检查7个项目。检索与源码审查能确认其声明、代码和依赖，不能替代本机安装测试；以下明确区分这两类证据。星数与README中的“official”不是官方背书或质量证明。

| 项目 | 实际是什么 | 对本项目的判断 |
|---|---|---|
| ahujasid/blender-mcp | Blender操作桥接，包含场景查询、截图和执行Python | 需要持续操作Blender UI时有用；当前已有bpy，桥接不是美术能力本身 |
| jithinolickal/blender | 真正的SKILL.md，强调拆分部件、多角度对照与里程碑 | 借鉴检查流程；GPU Cycles与UI上下文假设不宜原样套用 |
| alton47/threejs-skills | 材料、灯光、性能等技能说明合集 | 存在可复核的错误和旧API，不建议整包照搬 |
| Poly-Haven/polyhavenassets | 官方资产管理插件；素材库是另一层 | 先精选资产，不急于装全库插件；控制分辨率与风格一致性 |
| Hunyuan3D-2.1 | 生成形状与PBR贴图的模型 | 显存与许可条件不适合本机主线；生成结果仍需整理与动作验证 |
| TRELLIS.2 | 图像到PBR三维资产的生成模型 | 适合有条件的云端候选实验；不适合作为本机或实时演出依赖 |
| glTF Transform | 检查、验证和定向优化GLB的可执行工具 | 值得放进导出流程；它优化资产交付，不负责把造型变美 |

**Blender MCP。** MIT项目，核查提交c5f35d9：服务器提供截图和执行代码，插件通过socket在Blender里运行Python。已有headless bpy不等于已经安装并打开Blender桌面插件；当前版本的安全模式为可选，遥测有单独设置。若后续引入，应锁定提交，先验证连接和只读查询，再在项目副本中做小修改。[仓库及README](https://github.com/ahujasid/blender-mcp) · [执行能力源码](https://github.com/ahujasid/blender-mcp/blob/c5f35d9cc54451d785ac4c00c48bf9e98a2e8db9/src/blender_mcp/server.py)

**Blender skill。** Apache-2.0项目，核查提交6bfca49。多角度检查、修改前保存和部件分解有价值；范例偏家具，不能据此称为毛绒、人物与服装专业技能。它假定GPU Cycles和可用的UI上下文，导出到游戏还需要额外检查。[具体SKILL.md](https://github.com/jithinolickal/blender/blob/6bfca4973e7086696b08b108bfe6aae62ede33c0/skills/blender/SKILL.md)

**Three.js skills的反证。** 材料skill将非色彩贴图默认写为LinearSRGBColorSpace，而本项目r180官方Texture默认是NoColorSpace。性能skill将保留多材质group的合并描述为N次绘制变1次，但官方BufferGeometry说明各group独立绘制。合成一个Mesh不等于单次draw call。这个发现足以改变“直接安装整包”的建议。[材料skill](https://github.com/alton47/threejs-skills/blob/7b8e25638cff83a6be4926d8f05001022cc80ac3/skills/threejs-materials/SKILL.md) · [性能skill](https://github.com/alton47/threejs-skills/blob/7b8e25638cff83a6be4926d8f05001022cc80ac3/skills/threejs-performance/SKILL.md) · [r180 Texture](https://github.com/mrdoob/three.js/blob/r180/src/textures/Texture.js) · [r180 BufferGeometry](https://github.com/mrdoob/three.js/blob/r180/src/core/BufferGeometry.js)

**Poly Haven插件。** 插件GPL-3.0，核查源码声明Blender4.5.0；资产CC0不等于官网插件安装包免费。此时直接选择少量素材即可，不必先安装资产管理插件。[官方插件仓库](https://github.com/Poly-Haven/polyhavenassets)

**Hunyuan3D-2.1。** 官方README列出形状10GB显存、贴图21GB、合计29GB。其社区许可不是MIT/Apache，地域定义有欧盟、英国、韩国排除条款；如未来在芬兰等地使用，应按具体模型与服务条款重新核对。当前排除为本机主线，已不需要以本机试装来证明不适配。[官方仓库](https://github.com/Tencent-Hunyuan/Hunyuan3D-2.1) · [该版本许可证](https://github.com/Tencent-Hunyuan/Hunyuan3D-2.1/blob/82920d643c0dc2f7bfd7255f45f62d386edfe60c/LICENSE)

**TRELLIS.2。** 官方README要求Linux测试环境与至少24GB NVIDIA显存，示例实际调用CUDA；速度展示依赖H100等硬件。MIT不代表本机能运行，生成GLB也不代表已经有可用绑定或穿衣拓扑。可把它作为以后云端背景物候选实验，不能拿生成耗时替代资产可用性评测。[官方仓库](https://github.com/microsoft/TRELLIS.2) · [示例源码](https://github.com/microsoft/TRELLIS.2/blob/75fbf0183001ed9876c8dbb35de6b68552ee08bd/example.py)

**glTF Transform。** 当前CLI文档提供inspect、validate、贴图缩放和压缩等能力，并明确默认optimize未必适合所有场景。先看实际瓶颈再选操作；本项目在运行时控制熊、手臂和RoomSet，不能盲目flatten或join后破坏层级。[官方CLI](https://gltf-transform.dev/cli)

## 五、从第一性原理设计游戏：一次动作，为什么会让人感到被记得

最小构成不是“AI + 三维模型 + 特效”，而是：一个有意义的意图、一个能做出的动作、一个可感知的后果，以及后果与人物关系之间的联系。

本作品的核心循环可以是：我抱紧小熊 → 世界出现与这一下相关的光或节奏 → 我试着再做一次，确认关系 → 过了一段时间，姥爷用同样的停顿抱近他的小熊。即时反馈让人学会规则，延迟回调让这个规则成为故事。

MDA框架要求从目标体验倒推动态和机制，感官、叙事、联结、表达都可以是目标，竞争不是前提。它是一种设计框架，不是某个机制一定感人的实验结论。[Hunicke、LeBlanc、Zubek，2004](https://www.cs.northwestern.edu/~hunicke/MDA.pdf)

Agency Reconsidered区分忙碌的参与与有意图、可感知后果的行动，并讨论更强临场感也可能提高不合理期待、抑制探索的早期案例。由此推论：不要一开始藏掉所有提示；第一次试探的关系应清楚，之后才逐步变得诗意。[Wardrip-Fruin等，2009](https://cs.uky.edu/~sgware/reading/papers/wardripfruin2009agency.pdf)

具身交互研究强调真实材质、轻量试探、空间中的身体与共同参与，也不把直接的一对一映射视为全部价值。电脑游戏能检验探索、碰撞与反馈；真实小熊的重量、身体动作和共同在场仍需要线下试演。[Hornecker与Buur，CHI 2006](https://www.ehornecker.de/Papers/FrameworkCHI.pdf)

### 应借用与应避免的方法

| 借用游戏方法 | 用在本作品中 | 避免的误用 |
|---|---|---|
| 可读反馈 | 首次踏地就有局部金光，抱熊也能留下痕迹 | 不明原因的隐藏计数解锁 |
| 世界内线索 | 同款补线、熊的位置、光的方向暗示交换 | 一直用任务列表解释意义 |
| 状态与分支 | 六段骨架固定，停留和回调可不同 | 无限生成导致演员失去方向 |
| 纵向切片 | 一段“动作被记住”的美术、声音、互动和结尾同时成熟 | 只展示高质量截图，或只证明代码跑通 |
| 试玩与观察 | 看玩家如何试探，能否说清动作后果 | 用音量、点击数、兴奋程度当情感成功 |

纵向切片的制作意义可参考Volition的官方GDC讲座介绍；好奇心驱动探索可参考Outer Wilds编剧的官方讲座介绍。本轮只核查了这些讲座的介绍，未声称观看完整视频或获取其内部制作数据。[The Vertical Slice Challenge，2015](https://gdcvault.com/play/1022329/The-Vertical-Slice) · [Kelsey Beachum，2021](https://www.gdcvault.com/play/1027368/Independent-Games-Summit-Sparking-Curiosity)

## 六、戏剧与游戏的边界：固定结构可以容纳个人路径

轨迹研究区分作品预设的路径与参与者实际走过的路径，并讨论进入、过渡、重合与幕后调度。对本作品的推论是保留六段意义结构，让玩家如何抵达、停多久、哪个动作被记起有所不同；不必每场都生成一部新剧。[Benford等，CHI 2009，作者上传正文](https://www.researchgate.net/publication/221516077_From_interaction_to_trajectories_Designing_coherent_journeys_through_user_experiences)

一位真人姥爷与多位观众共享时间，不能无限同时提供每人的独占回应。“此刻接住一个人，其他人看见他被接住”，可以成为共同体验。AI可帮助检索和提出先前的动作细节；演员选择是否接住，舞台即时反馈不等待生成。

情绪曲线也需要落下和消化。追赶之后不立即再加奇观，而是逐渐退雨、停下来、给熊穿衣。关于强烈体验的研究讨论了高潮后的释放和反思，以及群体压力；它不是丧亲题材疗效证据。[Benford等，Uncomfortable Interactions，CHI 2012](https://people.cs.nott.ac.uk/pszjm2/uploads/2012/11/Uncomfortable-interactions.pdf)

## 七、下一版的制作顺序与改判条件

**第一步，完成一个可玩的空间。** 角色行走、转头、主要实体碰撞、上下文交互、暂停与重玩先成立。用户已选择独立电脑游戏；锁定官方Godot4.7.2，并核查下载摘要。使用Blender4.5.3母版导出GLB，避免额外依赖Blender桌面自动导入。Godot的CharacterBody3D提供可用于角色移动、墙面及斜坡碰撞的接口，仍需为本场景建碰撞体。[Godot角色接口](https://docs.godotengine.org/en/stable/classes/class_characterbody3d.html)

**第二步，集中完成熊与照顾片段。** 先让玩家手里的熊、交换区的大熊和姥爷怀里的熊具备同一身份，再检验手部动作。红窗与石板同步做到能烘托这一段的质量，而不是先扩建很多房间。

**第三步，完整走完六段。** 踏步、抱熊与哼唱有不同空间反馈；追赶与交换是行动，而非点击章节；结尾回应本场实际动作。保留安静路径。开发者或演员控制放在独立后台，不占据观众画面。

**第四步，在实际运行中比较。** 本轮程序测试只能证明状态正确；视觉检查只能证明指定视点下画面可读。至少还需要以下真人试演，才有资格判断是否更动人。

| 问题 | 小实验 | 什么结果会推翻当前方案 |
|---|---|---|
| 能否发现自己影响了空间 | 让少量新玩家自由进入，只提供一句情境；记录第一动作与试探 | 玩家普遍认为是自动播放：先修反馈与引导 |
| 能否认出自己的回调 | 比较通用动作与保留方向、次数、停顿的动作；不标注来源 | 只有字幕标签才能帮助认出：先改动作和视线 |
| 高质量建模是否有用 | 保持互动不变，对比占位资产与重点资产版本 | 看不清手部或景物抢戏：投资转向构图、光与动作 |
| 真人是否仍能即兴 | 测沉默、持续呼喊、多人同时动作；允许保持与拒绝建议 | 演员经常等AI或被晚到建议打断：减弱或停用自动提议 |

建议每轮先用3至4组小样本发现明显设计问题；这属于探索性试演建议，不足以形成统计意义上的普遍效果结论。

## 八、研究边界与思维痕迹

本轮结合本地源码与截图，核查7个GitHub项目、多篇原始论文、官方引擎文档和两个官方讲座介绍。对关键的技能错误、模型硬件要求、资产许可和游戏行动理论做了定向复核。更多同类工具列表已不太可能改变当前路线，因此停止扩张清单，转入可运行小样验证。

没有证明某个skill必然提高审美，也没有证明AI回调必然提高感动程度。未在本机运行大型3D生成模型，未安装未审查的skill合集；未把正式舞台的投影、传感器或演员质量视作已验证。软件版本与许可核查截至本报告日期，未来更换版本需要重新核对。

- 第一性拆解 → 若将独特体验等同于随机画面，会增加生成场景；改为优先保证动作、后果与延迟回调的可辨关系。
- 约束分析 → 若只追求理想画质，会先押注重型引擎与大模型；结合独立游戏需求和本机条件，选择可实测的Godot与Blender流程，保留以后迁移的资产母版。
- 逆向与证伪 → 若看到SKILL.md就安装，会带入错误或不适配的建议；源码对照后只采纳经验证的制作纪律，保持工具可替换。
- 机会成本 → 若只加面数，会减少动作与试玩投入；先完成一段能被认出的照顾，再根据玩家观察决定下一笔美术投入。
