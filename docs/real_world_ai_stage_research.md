# 《房间记得你》从网页原型到现实演绎：第一性原理研究与技术路线

> 研究日期：2026-09-03  
> 范围：把现有 Three.js 浏览器原型转成演员、观众与数字空间共同作用的现场体验。  
> 证据原则：只引用标准组织、官方文档、官方源码/开发指南与制作方的一手案例；带有“建议/阈值”的内容是本项目的设计判断，不冒充行业定律。

## 先给答案

### 问题一：需要具备哪些要素，注意什么？

不是先凑齐 VR、动捕、投影和 AI，而是建立一个可排练的闭环：

```text
人的意图
  → 可观察动作
  → 稳定识别（允许不确定）
  → 戏剧规则作出有限判断
  → 光 / 影像 / 声音改变
  → 演员和观众看懂改变
  → 人据此作出下一步行动
```

其中最重要的不是“识别得多”，而是三个条件：

1. **因果可读**：演员做了什么、空间为什么改变，参与者能在情感上理解。
2. **演员仍有主导权**：传感器只提供候选信号；戏剧状态由明确规则和现场操作员确认。
3. **失败仍能演完**：摄像头、网络或渲染失效时，演员、声音和基础灯光仍能完成整段。

### 问题二：用什么技术和工具？

当前最聪明的路线是：**先不用头显，把现有网页变成可排练的投影舞台；用普通摄像头读取一个演员的粗粒度动作；用本地控制页决定 `freeze / reject / release`；用声音和投影给出即时反馈。**

VR 是第二条可选分支，不是主干。只有当作品必须让一个人拥有“别人看不见的第一人称记忆空间”、必须用头部位置产生真实视差，或必须在不可能尺度中亲自移动时，头显才贡献了不可替代的戏剧价值。否则，投影与空间声音更能保留演员的脸、观众彼此可见和共同呼吸。

## 一、第一性原理：你到底在制造什么

现场演绎的最小单位不是“画面”，而是**可感知的关系变化**：一个人采取行动，另一个人或环境回应，新的意义因此产生。技术只有四种正当角色：

- **感知**：把身体、位置、声音或观众选择转为信号。
- **解释**：把连续且含噪的信号转成少数戏剧事件。
- **呈现**：用影像、声音、灯光或触觉让回应可感。
- **协调**：让演员、设备和操作员知道现在处于哪个节拍，并能恢复。

因此，系统的核心对象应该是“戏剧状态”，而不是设备：

```text
RECALL（召回）
  └─ approach_table → RECOGNITION（认出）
       ├─ hold_still → FREEZE（留下）
       ├─ refuse     → REJECT（拒绝版本）
       └─ walk_away  → RELEASE（放手）
```

现有原型已经拥有这个种子：三个记忆锚点、路径记录、`freeze`、`reject`、保存/离开，以及一个可替换的输入适配器。下一步应把键盘行为换成现场信号，而不是重写整个世界。

## 二、六组不可缺少的要素

| 层 | 必须回答的问题 | 最小交付物 | 最常见误区 |
|---|---|---|---|
| 戏剧 | 谁想要什么？空间何时回应？回应如何改变下一行动？ | 6 个节拍的“动作—系统回应—演员备选行动”谱 | 让技术变化很漂亮，却不改变角色关系 |
| 人与表演 | 演员能否预期系统？误识别时如何接戏？观众知道自己是否有影响吗？ | 演员训练规则、观众简短引导、每个互动的可见回执 | 把演员当动捕输入设备，把观众当遥控器 |
| 感知 | 哪个动作必须自动识别？置信度不足怎么办？ | 只识别 1–3 个粗动作；阈值、持续时间、冷却时间 | 一开始识别复杂手势、情绪或“内心状态” |
| 演出控制 | 谁拥有最终状态？如何 GO、HOLD、RESET、BLACKOUT？ | 单一状态机、舞台监督控制页、事件日志和快照 | 让传感器或生成模型直接控制灯光/剧情 |
| 安全与伦理 | 人能随时退出吗？失去视觉时会不会碰撞？身体/声音数据如何处理？ | 安全边界、看护员、停止手势、同意说明、默认不录像 | 把浏览器许可当成完整的知情同意 |
| 评估 | “成功”是技术没报错，还是观众感到关系成立？ | 行为数据 + 访谈 + 录像回看（经同意） | 只问“喜欢吗”，或只统计点击量 |

### 戏剧与参与设计

- 每个交互只能承担一个戏剧功能：靠近＝召回；停住＝留下；明确拒绝＝打碎当前版本。不要让同一动作在不同场景含义漂移。
- 把观众权力写清：**表达偏好、改变环境强度、选择有限分支**通常可控；“任意改变故事”会削弱演员准备和主题聚焦。
- 群体输入要聚合成趋势，而不是一人一票立刻改戏；显示“空间正在倾向哪一边”，让演员可以接受、抵抗或延迟回应。
- 互动必须有回执：0.2–0.5 秒内出现轻微声/光提示，随后才发生较大的戏剧变化。这是本项目的测试目标，不是通用标准。
- 为每个数字效果写一个反事实问题：“拔掉它，戏是否损失一个关系或选择？”如果只是损失装饰，先不做。

RSC 的《Dream》提供了有用的一手参照：它让远程观众在**关键节点**用触屏、触控板或鼠标化为萤火虫影响世界，同时让演员现场回应；演员动作还驱动互动配乐。该制作将现场表演、游戏引擎、动捕和网页观众入口分层，而不是让某个单一设备承担全部功能。[RSC《Dream》制作说明](https://www.rsc.org.uk/press/releases/live-performance-and-gaming-technology-come-together-to-explore-the-future-for-audiences-and-live-theatre)

### 演员与操作人员

最小团队不是“开发者一个人盯所有屏幕”，而是至少区分：

- 演员：知道系统可接受的动作区间，以及失效时的替代表演。
- 舞台监督/交互操作员：持有 `GO / HOLD / SKIP / RESET / BLACKOUT`。
- 技术操作员：监看追踪、渲染、音频、网络健康；小规模测试可与舞台监督合并，但正式演出不建议。
- 现场引导/看护员：如果使用头显，负责佩戴、边界、卫生、退出和摔倒风险。

排练要覆盖三种版本：正常运行、信号延迟、完全失效。演员需要知道“系统没回应时，我做什么”，而不是停下来等工程师。

### 安全、可访问性与心理边界

W3C 的 XR 可访问性需求明确提出：应支持多种输入方式、可重映射操作、清晰的开始/停止机制、方向复位、可调整互动时限、安全区、避免眩晕/闪烁诱因，并为依赖空间声音的体验提供替代方案。[W3C XR Accessibility User Requirements](https://www.w3.org/TR/xaur/)

转成本项目的硬约束：

- 头显参与者不自由穿越有桌椅、线缆和演员的舞台；若必须走动，使用清空的边界区和专人看护。
- 提供坐姿/站姿、动作/按钮两种等价输入；“不想做身体动作”不能导致被排除。
- 设置可识别的暂停/退出动作，并在物理世界中也有按钮或口头停止词。
- 禁止无法立刻停止的自动移动、强闪烁和突然失去地平线；给观众“降低运动/降低视觉强度”的选择。
- 先播放安全说明和设备校准，体验结束安排 1–2 分钟重新定向。
- 关于爷爷、失去和记忆的内容可能触发个人哀伤：提前说明主题、允许无解释退出，不诱导参与者公开私人记忆。
- 姿态、头部位置、声音都可能是敏感数据。WebXR 标准把 pose 与瞳距等明确视为敏感信息，并要求体现用户意图和同意。[W3C WebXR：Security, Privacy and Comfort](https://www.w3.org/TR/webxr/#security-privacy-and-comfort-considerations) 本项目默认只保留事件（如 `approach`），不保存原始视频、骨骼流或声音；评估录像另行明确同意。

## 三、VR 何时真的必要

先定义 VR 的不可替代能力：每个观众拥有独立的、随头部与身体位置更新的立体视点，并可完全遮蔽现实世界。WebXR 将 `immersive-vr` 定义为内容不与现实环境融合、独占沉浸式显示；沉浸会话至少提供观看者追踪。[W3C WebXR Device API](https://www.w3.org/TR/webxr/)

### 采用 VR 的必要条件

以下四项中至少两项为“是”，且第三项最好为“是”，才值得进入头显实验：

1. **私密视角**：同一现场中，不同观众必须看到不同的爷爷/房间版本。
2. **头部视差**：绕到桌椅背后、俯身、回头等 6DoF 行为本身承载意义，而非仅用于导航。
3. **现实遮蔽不可替代**：剧情必须让参与者暂时看不见剧场，投影、纱幕或灯光无法产生同等效果。
4. **单人或极小规模吞吐可接受**：作品接受逐人体验、佩戴校准、清洁、设备轮换与看护成本。

### 优先用投影/手机的条件

- 核心是演员与观众互相看见、共同等待、共同决定。
- “远处的人”的身体、面孔或真实距离是情感证据。
- 多人同步观看比私人视点重要。
- 互动只是选择、靠近、停留、声音或群体趋势。
- 需要低门槛巡演、快速复位或让行动能力不同的人平等进入。

### 对本项目的当前结论

**主版本先用投影 + 空间声音 + 摄像头/按钮；VR 只做一个 2–3 分钟的 A/B 支线。** 比较同一节拍在“共享投影”和“单人头显”里的差别。若头显没有显著提升“我亲自进入了记忆”的评分，或明显降低“我和演员/其他人同处一室”的感觉，就不把它升级为主介质。

## 四、推荐系统架构

### 原则

- **单一真相源**：只有 show server 写入当前戏剧状态。
- **事件与连续信号分离**：骨骼坐标不是剧情；先滤波、阈值化、去抖，再生成 `actor.approach` 等事件。
- **操作员在环**：高影响转换可自动“预备”，由操作员 GO；低影响环境变化可以自动。
- **输出解耦**：同一个 `memory.freeze` 事件分别驱动影像、声音、灯光，某一路失效不拖垮其他路。
- **本地优先**：演出核心不依赖公网；素材预载；有线 LAN 连接关键机器；观众 Wi‑Fi 与控制网隔离。
- **状态可恢复**：每条事件有 `showId / eventId / timestamp / source / confidence`；输出幂等；新客户端先取状态快照再收事件。

```text
                         ┌────────────────────┐
演员身体 ─ 摄像头 ──────→│ MediaPipe / 追踪层 │
                         └─────────┬──────────┘
                                   │ raw pose
按钮/脚踏/麦克风 ───────────────────┤
                                   ▼
                         ┌────────────────────┐
观众手机 ─ WebSocket ───→│ 输入解释器          │← 阈值/持续/冷却/聚合
                         └─────────┬──────────┘
                                   │ candidate events
                                   ▼
舞台监督控制页 ─ GO/HOLD→┌────────────────────┐
                         │ 本地 Show Server    │
                         │ 状态机 + 快照 + 日志 │
                         └───┬────┬────┬───────┘
                   WebSocket │    │OSC │OSC/sACN
                             ▼    ▼    ▼
                     Three.js/TD  音频  灯光台
                       投影画面   系统  （最终仲裁）
                             │
                             └─ 可选 WebXR / OpenXR 头显分支
```

### 工具选择：现在、以后、不要急着买

| 能力 | 现在建议 | 升级条件 | 依据 |
|---|---|---|---|
| 视觉世界 | 保留现有 Three.js，直接全屏投影 | 需要复杂投影映射、多路视频、实时材质合成时再接 TouchDesigner；需要高保真角色/虚拟制片时再评估 Unreal | Three.js 已有 `WebXRManager`，可在同一代码基上开启 XR，不必立刻迁移。[Three.js WebXRManager](https://threejs.org/docs/pages/WebXRManager.html) |
| 人体输入 | 普通 RGB 摄像头 + MediaPipe，只识别靠近、停住、双臂拒绝等粗动作 | 遮挡、暗光、多演员或精确肢体驱动连续失败，再用惯性/光学动捕 | MediaPipe Web Pose Landmarker 输出 33 个图像/世界地标和可见度；视频推理会阻塞主线程，官方建议放到 Web Worker。[Google Pose Landmarker for Web](https://developers.google.cn/edge/mediapipe/solutions/vision/pose_landmarker/web_js) |
| 实时消息 | 本地 Node 服务 + WebSocket；JSON 只传事件和快照 | 大规模远程观众才单独压测/扩容 | WebSocket 标准提供网页与服务端的双向通信接口。[WHATWG WebSockets](https://websockets.spec.whatwg.org/) |
| 软件间控制 | OSC：Show Server ↔ TouchDesigner/音频软件 | 需要时间码与帧同步时另加专业同步系统 | OSC 是开放、与传输无关的消息协议；TouchDesigner 官方提供 OSC In/Out CHOP 与 DAT。[OSC 1.0](https://opensoundcontrol.stanford.edu/spec-1_0.html)、[TouchDesigner OSC](https://derivative.ca/UserGuide/OSC) |
| 灯光 | 由灯光台执行预编程 cue；Show Server/TD 只发触发或参数建议 | 充分排练后才允许低风险灯光参数自动变化 | TouchDesigner 能发 DMX、Art‑Net、sACN；官方提醒 DMX512 设备最大刷新率 44Hz，可靠使用应不高于此。[TouchDesigner DMX Out CHOP](https://docs.derivative.ca/DMX_Out_CHOP)、[ANSI E1.31 sACN](https://tsp.esta.org/tsp/documents/docs/E1-31-2016.pdf) |
| 空间声音 | 第一轮用立体声/四声道预设 cue；浏览器版可用 Web Audio | 只有移动声源与演员位置关系被验证有意义时，才上多声道对象式系统 | Web Audio 的 `PannerNode` 能相对监听者在三维空间定位声音，并提供 equal-power 与 HRTF 模式；Web 版 HRTF 输出是双声道，不等同于剧场多扬声器系统。[W3C Web Audio](https://www.w3.org/TR/webaudio-1.0/#Spatialization-section) |
| VR | 先用当前 Three.js 加一个 WebXR 可选入口做 A/B | 需要稳定的独立应用、多厂商头显和更复杂交互时，再转 Unity/Unreal + OpenXR | WebXR 应先检查会话支持并由用户主动开始；OpenXR 在应用与各厂商 runtime 间提供共同接口。[W3C WebXR](https://www.w3.org/TR/webxr/)、[Khronos OpenXR Registry](https://registry.khronos.org/OpenXR/) |

不要在第一阶段同时引入 Unreal、TouchDesigner、完整动捕、VR 和多手机网络；那会让你无法判断体验提升来自哪里，也会把排练变成系统集成测试。

## 五、未来 2–4 周最值得做的实验

### 实验问题

> 当演员靠近、停住或拒绝一个记忆锚点时，投影和声音的回应能否被演员可靠地接住，并让观众理解“越想看清，记忆越不稳定”？

### 最小设备

- 现有 Windows 笔记本和网页原型
- 一台普通投影机或大屏
- 一个 1080p 摄像头（现有手机摄像头也可先替代）
- 立体声音箱；有条件再加后方两只
- 一个本地路由器；关键演出机尽量接网线
- 手机/平板作为舞台监督控制页
- 地面胶带、安全照明、一个真实绿色桌椅

此阶段**不采购头显、动捕服、媒体服务器或灯光网络设备**。

### 第 1 周：先让戏成立

1. 固定一个 5 分钟、6 节拍版本。
2. 把原型状态抽为 `recall / distort / freeze / reject / release`。
3. 做舞台监督控制页：GO、HOLD、BACK、RESET、BLACKOUT。
4. 投影现有画面；声音先用固定 cue；演员完整演三遍。

通过条件：不用解释技术，3 位观察者中至少 2 位能说出“演员的动作改变了空间”，并能指出哪一次变化代表拒绝或留下。

### 第 2 周：只接一个身体输入

1. MediaPipe 放 Web Worker，输入摄像头。
2. 只实现一个事件，例如：演员进入桌边区域并停留 1 秒 → `actor.approach_table`。
3. 加平滑、迟滞、持续时间、2 秒冷却；置信度不足时不触发。
4. 操作员看到“候选事件”，按 GO 确认；连续演 10 次并记录漏触发/误触发和端到端延迟。

通过条件：10 次中至少 9 次在演员预期的节拍触发；误触发不超过 1 次；演员无需看技术屏幕；P95“动作成立 → 轻反馈出现”小于 200ms。阈值是本轮工程验收线，应根据设备实测修订。

### 第 3 周：接入观众，但限制权力

1. 手机扫码进入本地网页，只在一个节点选择“留下/放手”。
2. Show Server 聚合 5–10 人的输入，显示倾向和人数；不把单个选择直接写入状态。
3. 演员先看到环境暗示，再决定接受或抵抗群体倾向。
4. 网络断开时自动回到预设分支，不中断演出。

通过条件：至少 80% 参与者能在演后准确描述自己的选择如何被作品回应；演员认为观众输入提供了可表演的刺激，而非打断节奏。

### 第 4 周（可选）：VR 反事实实验

只把“远处的人没有回头”做成 2–3 分钟 WebXR 场景；内容、声音和台词尽量与投影版一致。不要扩写第二套作品。

随机让 6–10 位测试者分别体验两个版本，记录：

- `进入记忆感`（1–7）
- `与演员/他人在一起的感觉`（1–7）
- `不适/眩晕`（0–3）
- 穿戴、校准、复位的分钟数
- 能否说清选择与回应的因果关系

只有当 VR 的“进入记忆感”明显提高（本小样本建议至少平均 +1.5/7），且没有让共同在场感、可访问性和复位时间付出不可接受代价，才继续投资。否则保留为档案或单人附加体验。

WebXR 并非所有主流浏览器都完整支持，而且沉浸会话涉及安全上下文、用户主动触发与权限；必须先做设备能力检测并提供非 XR 回退。[WebXR 规范的应用流程](https://www.w3.org/TR/webxr/#application-flow) 正式测试应由 `localhost` 或 HTTPS 提供内容，不以当前 `file://` 打开方式作为部署方案。

## 六、事件接口：让所有工具可以替换

建议从第一天就采用语义事件，不把设备名字写进剧情：

```json
{
  "showId": "room-v01-run-07",
  "eventId": 184,
  "time": 1788427712.241,
  "source": "actor-tracker-1",
  "type": "actor.approach",
  "target": "green-table",
  "confidence": 0.91,
  "phase": "candidate"
}
```

操作员确认后生成新的领域事件：

```json
{
  "eventId": 185,
  "type": "memory.recall",
  "target": "green-table",
  "phase": "committed",
  "stateVersion": 12
}
```

这样，今天的 MediaPipe 可以换成明天的动捕；Three.js 可以换成 TouchDesigner 或 Unreal；剧本和排练语言不变。

## 七、必须主动测试的失败模式

| 失败 | 观众表面看到什么 | 设计上的处理 |
|---|---|---|
| 摄像头遮挡/暗光 | 动作没有回应或错误回应 | 置信度门槛；操作员手动 GO；演员有不依赖系统的替代动作 |
| 抖动和重复触发 | 画面闪动、cue 连发 | 平滑、迟滞、持续阈值、冷却、事件幂等 |
| Wi‑Fi 拥塞 | 观众选择延迟 | 核心控制走有线；观众网隔离；超时进入预设分支 |
| 客户端状态不同步 | 不同输出处于不同记忆版本 | 版本号、周期快照、重连先全量同步 |
| 渲染掉帧 | 观众不适、演员失去节奏 | 素材预载；性能上限；一键切到静态画面/黑场；不要在演出时生成关键画面 |
| 音画漂移 | 动作与意义脱节 | 为事件统一时间戳；用操作员 cue 保底；升级后再引入 timecode/genlock |
| 模型把路人当演员 | 无意触发 | 摄像头取景限区、单人 ID/区域门控、候选事件确认 |
| 头显失去追踪/边界 | 漂移、碰撞、恐慌 | 清空体验区、看护员、物理停止、立即透视/摘除流程 |
| 自动化越权 | 传感器直接黑场或改变关键剧情 | 高影响事件只能提交候选；舞台监督持有最终仲裁与独立 blackout |
| 参与者情绪过载 | 不愿继续但不敢退出 | 开场内容提示、明确无解释退出、引导员观察、结束后重新定向 |

## 八、如何判断作品而不是设备成功

每轮只回答四类问题：

1. **可懂性**：参与者能否说出“我/演员做了 X，所以空间发生 Y”？
2. **能动性**：选择是否改变了下一段体验，而不只是颜色或粒子？
3. **表演性**：系统回应是否给演员新的可行动对象？演员能否接住延迟和失败？
4. **代价**：搭建、校准、复位、看护和故障恢复是否与戏剧增益相称？

建议每场记录：状态事件日志、触发成功率、P50/P95 延迟、操作员接管次数、复位时间；演后只问 4–6 个开放问题，再让参与者画出他们理解的“动作—回应”链。原始视频、骨骼和声音默认不留存。

## 九、最终推荐

**未来两周只做“真实演员 + 真实绿桌椅 + 投影 + 声音 + 一个被可靠识别的动作 + 人工可接管的状态机”。** 这是从网页到现实世界的第一座桥。

完成这个闭环后再依次增加：观众手机聚合 → OSC/TouchDesigner → 灯光 cue → 单段 WebXR A/B。不要把 VR 当成“更真实”的默认答案；对《房间记得你》而言，技术的工作不是替代人的在场，而是让记忆对人的行动作出可演、可懂、可恢复的回应。

RSC 的经验也支持这种分层思路：其《Dream》用 7×7 米动捕区、LED 背景、Unreal、灯光台、预制动画、网页观众入口和互动配乐组成协作管线，并强调这是现场戏剧的新补充而非对现实剧场的替代。[RSC《Dream》技术细节](https://www.rsc.org.uk/press/releases/live-performance-and-gaming-technology-come-together-to-explore-the-future-for-audiences-and-live-theatre) RSC 后续研究仍把低延迟、多通道服务、物理与数字对象的对应，以及技术限制列为持续研究问题，说明这些不是购买一套设备就会自动消失的难题。[RSC Digital Embodiment](https://if.rsc.org.uk/learnings/digital-embodiment/)

## 思维痕迹

- 第一性原理 → 不拆解时会把目标定义为“把网页做成 VR”；拆到现场戏剧的基本单位后，改判为“先证明人的动作能产生可读、可接续的关系变化”，VR 降为可选输出。
- 约束理论 → 不使用它会同时开发追踪、VR、投影、声音和观众网络；识别到当前瓶颈是尚未验证的演员—空间反馈后，只投资一个动作闭环，其他能力暂缓。
- 逆向＋证伪 → 不做对抗会把沉浸感提升默认归功于头显；加入同内容的投影/VR A/B 后，VR 必须在进入记忆感上产生足够增益且不严重损害共同在场、舒适和复位成本，否则不进入主线。
- 安全工程的可失败设计 → 不使用它会让识别模型直接改变剧情和灯光；改成“候选事件—人工确认—可回退 cue”，传感器、网络或渲染单点失败时仍能演完。
